# 常驻 DOCX 构建实验与 benchmark

> 历史实验记录：文中 JSONL worker、benchmark 脚本及关闭 SVG 备用图的实验开关
> 已在预览接入后的清理中删除。以下命令与接口仅描述当时的归档版本，不适用于当前源码。
> 当前实现见 [DOCX 实时预览](DOCX_LIVE_PREVIEW.md)。

日期：2026-10-31。范围：仅修改 Papper，尚未接入 VS Code 扩展。

后续的 SVG 专项改动与配对结果见 [SVG → PNG 热构建优化](SVG_FILTER_BENCHMARK.md)。
本报告保留首次常驻原型的历史测量，未将后续优化混入基线。
后续已完成服务内置 PDF 和扩展编辑刷新，见 [实时预览接入记录](DOCX_LIVE_PREVIEW.md)。

当前原型在含公式、图片和引用的文稿上，将连续编辑后的 DOCX 热构建缩短约
11%–18%，完成 PDF 的总等待缩短约 10%–17%。收益有限：37 页真实论文仍需约
5.8–5.9 秒完成 DOCX 和 PDF；200 页纯文本的 DOCX 构建反而慢约 5%。
新增载荷约 155 KiB，相同资源外置布局的压缩 wheel 增加约 54 KiB。
速度和长文稿上的退步需要继续评估，不能据此承诺接近即时的连续编辑预览。

## 实现范围

- 新增隐藏入口 `papper __docx_worker`，通过 stdin/stdout JSONL 接收构建请求。
- 同一项目复用 Rust 宿主进程、原生 Pandoc worker 和现有文献依赖缓存。
- 支持传入未保存的 Markdown 缓冲区，不写回源文件。
- 每次重新读取样式、元数据和 reference DOCX，执行完整图片、公式和 DOCX 封装流程。
- 复用既有图片、公式磁盘缓存，没有“原文未变就直接返回上次结果”的整文缓存。
- 构建失败保留上次成功的 DOCX，下一次有效请求继续处理；stdin EOF 关闭所拥有的进程。
- 修复 Windows 常驻进程中的 Lua 环境读取问题：使用请求当前的环境值，避免
  MathType 标记、交叉引用及页眉页脚控制沿用先前请求的设置。

没有新增运行时依赖或修改扩展的自动刷新逻辑。协议目前串行处理请求，尚不包含
编辑器防抖、队列合并、过期结果丢弃、中途取消、文件监听及可发现的共享服务。
现有 HTML 预览保留独立的启动选项缓存。

## 测量方法

机器为 Windows x64、Intel Core i7-13700KF、约 64 GiB RAM。使用相同 Release
构建设置，比较修改前存档的 CLI、worker 和 Lua 资源与新常驻路径。
修改前代码基于 `edc17dd891ab1490799abdef0def487ba0595d46`；工作区原有模板修改
保留并作为两条路径的共同输入。二进制和输入 SHA-256 保存在原始 JSON 中。

每个场景先预热 2 轮，再测量 12 轮；每轮都做不同的、可见的正文、公式或引用修改，
随机交错普通 CLI 和常驻路径的先后顺序。两条路径使用各自独立的状态目录和缓存。
真实稿件只读，所有输出写入实验目录。测量期间不并行运行编译或测试。

普通 CLI 从启动进程计时至退出；常驻路径从发送完整 JSON 请求计时至收到已完成
DOCX 的回复，包含缓冲区传输。常驻宿主的启动耗时另存，不计入热构建。
两条路径随后都启动同一份 Docxide CLI 0.20.1，生成完整 PDF。
总时间为该轮实际 DOCX 与 PDF 两段耗时之和，再计算中位数。

这里的“总时间”不包含编辑器防抖、Webview 消息传输、PDF.js 绘制和屏幕刷新。
Docxide 仍然全量生成 PDF；扩展现有的可见页绘制不会让这里的 PDF 生成自动变成增量。

## 首次构建、正确性与剩余耗时

项目公式／图片缓存为空时，真实论文首次构建为普通 CLI 57.261 秒、常驻路径
57.879 秒，随后 Docxide 分别约 0.645、0.650 秒。未清空操作系统文件缓存，
这不是严格的整机冷启动测试。常驻进程不能消除首次公式转换的成本。

70 组有效配对（含预热）全部检查规范化后的 DOCX XML、样式、普通图片和
MathType MTEF 数据，并逐页比较 Docxide PDF 在 72 dpi 下的像素。
SDK 写出的 OLE 头和 WMF/GDI 包装含波动字节，因此不做整个 ZIP 或公式包装的
逐字节相等断言：MTEF 去掉 28 字节 OLE 原生头后精确比较，WMF 结合长度和
完整 PDF 像素检查。此验证覆盖 Docxide 的输出，不等于独立验证 Word 的每种排版。

第一次正式运行已完成两个模板场景，随后论文首次构建中出现一次外部 MathType
SDK `MTAPIConnect(prefs)` 状态 -2，导致单个公式退回另一条转换路径、尺寸改变。
一致性检查拒绝了该配对并停止运行；失败日志保留。模板已完成的数据有效。
论文与长稿随后重新运行，所有配对通过检查。该失败没有作为速度样本混入统计。

常驻构建各阶段中位数如下，单位毫秒。Pandoc 阶段包括依赖检查和转换，
依赖检查本身约 3–7 ms；不能将两个阶段重复相加。

| 场景 | 准备 | Pandoc／Lua／写 DOCX | DOCX／公式最终封装 |
| --- | ---: | ---: | ---: |
| 模板正文 | 37 | 1,181 | 58 |
| 模板公式 | 36 | 1,180 | 377 |
| 论文正文 | 39 | 4,077 | 1,135 |
| 论文引用 | 40 | 4,008 | 1,095 |
| 200 页纯文本 | 42 | 968 | 29 |

模板的 `svg_to_png` 过滤器约需 1 秒，真实论文的一次热样本约需 2.25 秒；
现有过滤器路径仍启动辅助程序获取字体等信息。图片缓存命中不代表这段调用免费。
同时，Pandoc 全文转换和含图片的 DOCX ZIP 写出、公式后处理仍然执行。
缓存命中率也随编辑而变：论文正文的文献缓存命中 12/12，引用编辑仅为 2/12。

200 页纯文本没有获得净收益，约 55 ms 的退步还未定位；现有分段数据不足以将它
归因于 JSON 传输或某个具体内部步骤，应先继续 profiling。需要区分“保持进程常驻”
与“按受影响章节／资源做增量构建”，本次只实现前者及既有缓存复用。

真实论文热构建后的一次采样中，Rust 宿主与 Pandoc worker 的工作集合计约
161.7 MiB，私有提交内存合计约 98.6 MiB。这是单个时刻的观察，不是峰值或
相对普通 CLI 的增量。进程关闭后这些常驻资源随之释放。

原生程序均为相同设置的非嵌入 Release 构建。wheel 对比包含旧、新 Lua 资源和
worker 源码，统一使用同一个小型 `pmt.exe` 启动器，再以相同 Deflate level 6
重打包；重新生成并逐项验证 `RECORD` 的 SHA-256 和大小，同时验证 ZIP 完整性。
两份 wheel 的压缩方法和布局完全一致。解压载荷不包含文件系统簇分配、安装器
生成的元数据或用户缓存。

官方打包器另做了一组“相同新资源，仅替换原生程序”的 `--prebuilt` 对照，
wheel 为 64,140,926 → 64,193,284 B，增加 52,358 B。它用来确认原生增量，
不是上表的完整历史资源比较。

**正式发行默认的内嵌 runtime／static CRT 布局尚未完整重编译测量。上表的
54.2 KiB 不能直接当作正式发行 wheel 的精确增量。** 已测数据说明，本功能在
当前构建方式下增加约 155 KiB 载荷，没有引入新的整套转换引擎。
Docxide CLI 本身固定为 9,796,096 B，两条路径共用，本次没有将它新打包进 Papper。

## 回归检查与复现

新增四个测试，覆盖未保存缓冲区及普通 CLI 输出一致性、请求间页眉页脚清理、
同路径文献修改与失败保留上次输出、样式更新及 reference 保护、MathType 开关的
请求环境更新。最终相关检查共 63 项通过。

最初全量运行另外有两个已有模板快照失败：`html-template`、`docx-template`。
使用修改前的 CLI 也复现了这两个失败，原因是工作区模板已有内容修改。
没有修改模板内容或更新这些快照。最终针对其余用例复查：61 项通过，加上两项
中文模板快照单独复查通过。Release 编译及格式检查通过。

测量入口：`scripts/benchmark_docx_worker.py`。本机产物目录为
`output/benchmarks/docx-resident-20261031/`，包含：

原始逐轮耗时、DOCX、PDF、日志和输入身份保存在：

## 对接入扩展的判断

体积成本较小。当前收益可以缩短停顿后或保存后的刷新等待，但还不足以让真实
复杂论文实现低延迟的按键跟随预览。建议先保留为实验原型，优先分析 SVG／字体
辅助调用、全文写出和纯文本退步，再决定是否花精力接扩展。

若按当前性能接入，应保留上一次预览并合并编辑请求：一次只构建一个版本，
待处理队列只保留最新缓冲区，完成时丢弃过期结果。可见页绘制和滚动／缩放保留
仍由现有预览层负责。该接入决策和实现不属于本轮修改。
