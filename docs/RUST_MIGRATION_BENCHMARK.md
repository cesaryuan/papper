# Rust 迁移的 HTML Server 构建基准

2026-10-02，在 Windows x86_64 开发机上，最终通过 `uv tool` 安装的原生程序对真实论文进行连续热构建：修改正文后，完整 CLI 的中位耗时从 **560.11ms 降到 241.20ms，减少 56.9%**；正文和依赖内容不变时，从 **360.06ms 降到 47.36ms，减少 86.8%**。每个场景采集 15 对正式样本。此结果覆盖新的 CLI 进程启动、配置处理、服务校验、构建请求和 HTML 发布，反映当前 Windows 制品在这些输入上的热构建性能。

实验遵循以下步骤和边界：

1. 每种实现拥有独立的稿件与样式副本、输出文件、服务端口及服务状态。原稿只读；实验结束后重新校验原稿 SHA-256。资源目录保持相同，并以原有只读资源为基础解析图片、参考文献和 CSL。
2. Python 基线通过开发虚拟环境的 `python.exe -m pandoc_manuscript.cli` 调用保留在 `tests/legacy/` 的完整实现。Rust 通过冻结的原生可执行文件直接调用；安装包测量用的是 `uv tool` 安装后与 wheel 中入口字节一致的程序。安装过程发生在计时之前。每次测量均创建一个新的 CLI 进程并捕获其完整输出。
3. 两种实现都执行 `build html -m <稿件副本> -o <输出副本> --start-server --server-port <独立端口> --resource-path <相同资源根>`。计时从创建 CLI 进程之前开始，到进程成功退出且完成 HTML 发布为止。程序每次都写入输出；服务命中 HTML 缓存的场景也包含输出文件发布成本。
4. 每个场景先做 2 对预热，再做正式配对样本。每一对采用相同的正文编辑；在固定随机种子 `20261002` 下交错两种实现的调用顺序。修改正文场景保持引文与资源内容不变，要求正文确实更新；内容相同场景要求整个 HTML 缓存命中。每次观察请求计数、HTML 命中计数和 citeproc 命中计数。
5. 每一对比较完整 HTML，仅统一换行符与文件末尾空白。源码正式轮包含预热在内的 68 对输出全部一致；安装包 5 对初测包含预热的 14 对输出一致；安装包 15 对正式轮包含预热的 34 对输出一致。原始样本、HTML 摘要、配置和冻结可执行文件保存在各自实验目录。
6. 两种实现均设置 `PAPPER_DISABLE_UPDATE_CHECK=1`。旧 Python 实现尚不支持该开关，因此为它预置独立且新鲜的更新缓存，阻止后台更新网络请求，保留完整 CLI 入口与正常缓存读取。最终安装包测量移除 `PAPPER_RESOURCE_ROOT`，通过记录的 `resource_root` 确认实际使用内嵌运行时；其 Haskell Worker 字节摘要与基线相同。
7. 全部正式样本参与统计。减时比例为 `1 - Rust中位数 / Python中位数`。p95 使用排序样本的零起点下标 `min(n-1, floor(0.95*n))`；15 个样本下该值对应最高样本，用于显示本轮较慢情况。最终安装包实验在完整测试和编译结束后运行，期间没有并行测试或构建任务。

阶段分析帮助确定了这次提速的来源。以下是源码构建的诊断采样，其用途是定位开销，不能替代完整 CLI 配对结果。

| 诊断边界 | 观测 |
| --- | --- |
| 实际 `ureq` GET `/version`，读取 JSON，500ms 超时 | 热请求中位约 0.6–0.8ms |
| 大图片摘要缓存修复前，真实论文 POST `/convert/raw` | 热请求约 49–52ms，其中资源验证约 44–49ms |
| 大图片摘要独立缓存后，同一论文 POST `/convert/raw` | 热请求中位 7.82ms，资源验证约 6ms |
| 修复后的 public `build_html` 库边界 | 同一论文约 12ms，包含服务验证与输出发布 |
| 生产 `atomic_write` 发布相同 HTML | 约 1.2–1.4ms |
| 最小 CLI `--help` / `--version` | 冻结的源码 Release 可执行文件约 39–40ms |

大图片开销来自原有 32MB 字节缓存的反复清空：真实论文引用的图片总量超过缓存预算，遍历依赖时不断重新读取并计算摘要。修复把文件身份、变更时间及 SHA-256 摘要独立缓存，按 64KiB 流式计算首次摘要，避免为了校验资源而长期保存所有大图片字节。依赖图缓存复用已解析的 YAML、CSL 与模板引用，同时继续检查已选文件和尚不存在的高优先候选；Windows 文件检查包含身份和 ChangeTime，恢复 mtime 也会使真实改动失效。远程引用继续遵循验证周期和条件请求。

完整 CLI 与 HTTP 的固定差额主要出现在进程启动。12 次单独 `--version` 采样中，冻结源码 Release 的 `CreateProcess` 返回耗时中位 31.05ms，完整退出 38.87ms；最小 131KiB Rust 程序分别为 2.94ms 和 6.56ms。该结果定位了 Windows 进程创建和映像加载成本，尚不足以确定其中操作系统、文件系统或安全扫描各自的贡献。实际 HTTP 采样没有显示 40ms 的 Nagle 延迟。最终安装包约 90.28MB，其完整 CLI 已在上面的实际安装包实验中计时。

性能实验结束后，交付 wheel 同步了 README 说明文字。逐 ZIP 条目比较确认仅 `METADATA` 与 `RECORD` 改变，原生入口、别名入口、运行时归档及已安装程序的字节全部保持一致。因此保留测量来源 wheel 的身份，同时记录新的交付 wheel 身份；以上性能结果对应相同的产品程序与运行时。

Rust 源码树身份覆盖根目录 `Cargo.toml`、`Cargo.lock`、`rust-toolchain.toml`、存在的 `.cargo/config.toml` 及 `crates/` 下全部文件。先计算每个文件的 SHA-256，再按仓库相对路径排序，连接 `UTF8路径 + NUL + ASCII文件摘要 + 换行` 后计算总摘要。Python 基线用同一算法汇总实验开始时冻结的 `tests/legacy/` 下 `.py` 文件摘要。最终制品对应此次迁移的工作区源码；实验记录的基准 Git HEAD 为 `55f0d9ccb86a66495b8939e62a8f259da7ba5021`，源码树摘要用于区分当时尚未提交的修改。编译器为 `rustc 1.98.0 (88d9e12ae 2026-08-18)`，保留的 Worker 报告 Pandoc 3.12、Lua 5.4。
