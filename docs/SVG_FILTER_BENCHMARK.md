# SVG → PNG 热构建优化

> 历史实验记录：文中 JSONL worker、benchmark 脚本及关闭 SVG 备用图的实验开关
> 已在预览接入后的清理中删除。以下命令与接口仅描述当时的归档版本，不适用于当前源码。
> 当前实现见 [DOCX 实时预览](DOCX_LIVE_PREVIEW.md)。

日期：2026-10-31。本次在已经实现的常驻 DOCX 原型上，只优化 SVG 处理，尚未接入扩展。

37 页真实论文的 12 轮配对测量中，SVG 过滤器中位数从 2.207 秒降到 0.822 秒，
减少 62.7%；完整 DOCX 构建从 5.012 秒降到 3.598 秒，减少 28.2%；
再加上 Docxide 生成完整 PDF，从 5.664 秒降到 4.244 秒，减少 25.1%。

## 两项改动

### Windows 字体身份复用

此前，`svg_to_png.lua` 遇到文字或可能含文字的嵌套图片时，每轮都启动一次
`papper-svg font-identity`。它加载系统字体数据库，再按字体字节和选择顺序计算
哈希。图片最终命中缓存，也要先付出这部分成本。

现在 helper 在已有 SVG 缓存目录保存一个 195 B 的字体身份记录。每次仍枚举
fontdb 0.23 实际扫描的 Windows 系统及两个用户字体目录，按原顺序检查：

- 字体文件路径、清单及遍历顺序。
- 文件 ID、卷身份、长度、创建时间、写入时间及 Windows ChangeTime。
- helper 自身的内容身份，避免升级字体解析器或默认字体选择后复用旧结果。

这些信息均未变化时，复用此前由实际字体字节生成的身份。新增、删除、替换字体
都会失效；同大小修改并恢复 mtime，也会由 ChangeTime 检测到。
不以 TTL 或仅 mtime/大小作为命中条件。

扫描前后清单不同，不发布缓存；符号链接、无法读取的目录或不可靠的元数据均
回退完整扫描。损坏记录、不可写缓存也不能阻断正常图片输出。缓存仍通过同目录
临时文件原子发布；`PAPPER_SVG_TRACE=1` 可观察命中、失效和回退。
Linux/macOS 保留原有完整字体扫描，本轮没有扩展其平台字体发现规则。

### 避免 Lua 逐字节扫描长属性

SVG 的词法扫描器原来逐字符寻找标签结尾；每个字符都会生成一个 Lua 子字符串。
图中有很长的 base64 图片 href 时，即使 PNG 已缓存，仍会完整执行这个循环。

现在用原生字符串查找定位引号或 `>`，进入引号后直接查找配对引号。
大段 base64 不再经过逐字节 Lua 循环。属性里的 `>`、单引号和双引号边界、
DOCTYPE、损坏 XML 的拒绝行为均保持。SVG 和子资源仍读取实际内容进行指纹验证。

## 配对测试方法

机器与上一轮相同：Windows x64、i7-13700KF、约 64 GiB RAM。输入为相邻项目
`1-3d-mesh/manuscript.md` 的副本，输出 37 页，含大量媒体和 193 个 MathType 公式。
该论文项目自己的 `style.yml` 显式设置 `docxConvertSvgToPng: true`、
`docxEmbedSvgImages: false`，覆盖 Papper 默认的 `docxConvertSvgToPng: false`。
正文的一张图还单独标注了 `to-png=true`。因此本次测量是开启全局 SVG 栅格化的
项目负载，不能代表默认关闭全局转换时的开销或收益。benchmark 复制原配置，
没有为了测试临时开启这个开关。

两条路径都使用上一轮已存档的同一份常驻 Release CLI 和同一份原生 Pandoc worker，
当前相同的样式、DOCX 控制和其他 Lua 过滤器。仅切换：

- 修改前的 SVG helper、SVG 词法扫描器。
- 修改后的 SVG helper、SVG 词法扫描器。

固定 CLI 同时固定了传给图片缓存的 renderer ID，以隔离本次缓存／扫描改动。
渲染后端及实际图片输出没有改变；正常重编译 CLI 仍会按新 helper 源码生成新的
renderer ID，以保护后续升级的缓存失效。

两条路径从上一轮已验证的图片／公式缓存分别复制相同起点。先预热 2 轮，再测
12 轮，每轮追加不同的正文，随机交错两条路径的执行顺序。源 Markdown 在磁盘
保持原始内容，两条路径都通过 JSONL 传入同一个未保存缓冲区。
本轮用于比较热编辑，不能用于声称首次公式转换变快。

每轮计时包含完整 DOCX 请求至完成回复；随后都用同一个 Docxide CLI 0.20.1
生成完整 PDF。未计入编辑器防抖、Webview 传输和 PDF.js 绘制。
计时期间未并行运行编译或测试。源稿件保持只读。

## 结果

以下为 12 个正式样本的中位数和最近秩 p95，单位秒；12 个样本的 p95 即样本最大值。

| 指标 | 优化前中位数 | 优化后中位数 | 耗时减少 | 优化前 p95 | 优化后 p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| SVG → PNG 过滤器 | 2.207 | 0.822 | 62.7% | 2.359 | 0.877 |
| 完整 DOCX 构建 | 5.012 | 3.598 | 28.2% | 5.304 | 3.972 |
| Docxide 生成 PDF | 0.651 | 0.648 | 约 0.5% | 0.671 | 0.693 |
| DOCX＋完整 PDF | 5.664 | 4.244 | 25.1% | 5.975 | 4.622 |

各项中位数独立计算，不能要求逐项相加严格等于总时间中位数。
Docxide 没有改动，其微小时间差不作为优化收益。
与上一轮 benchmark 的绝对数字有波动，应使用本轮同场配对比较。

没有做“仅字体”“仅扫描器”的完整论文消融测量，因此不能把 1.38 秒的 SVG
节省量精确分摊给两项改动。初步 helper 小样本显示，完整字体指纹约需 1 秒，
热缓存检查约 0.1 秒；该小样本只用于定位，不作为上表的正式收益依据。

## 正确性和体积

全部 14 组配对（含预热）通过规范化 DOCX XML／样式／媒体／MathType MTEF
检查，以及每页 Docxide PDF 在 72 dpi 下的像素相等检查。没有关闭公式、降低图片
分辨率或绕过子资源内容失效来获得这次提速。MathType 热缓存保持 193/193 命中。

相关自动检查覆盖：字体安装、删除、同大小替换后恢复 mtime、损坏身份记录、
不可用缓存、SVG／SVGZ、嵌套图片修改、DOCTYPE、属性内引号／大于号，以及
失败保留先前输出；另复查常驻 DOCX 的缓冲区、依赖失效和请求环境行为。
这些相关检查共 31 项通过；另有 HTML／DOCX 的 SVG rasterization 快照 2 项通过，
合计 33 项相关检查通过。Release helper 编译、格式和差异检查通过。

Release `papper-svg.exe` 为 18,933,760 → 18,959,360 B，增加
25,600 B，即 25.0 KiB。`windows-sys` 已存在于工作区依赖，本次只给 helper
增加该依赖关系，没有引入新的包版本。本次没有重新打包完整发行 wheel，不能将
这 25 KiB 直接视为压缩安装包增量；上一轮体积报告仍对应上一轮版本。

## 产物与复现

入口：`scripts/benchmark_svg_filter.py`。

```powershell
cargo build --locked --offline --release -p papper-svg
uv run --no-sync python scripts/benchmark_svg_filter.py
```

本次原始结果：`output/benchmarks/svg-filter/20261031T043119.616382Z/results.json`。
同目录保留逐轮样本、工具 SHA-256、DOCX、PDF、两条路径的运行时副本和日志。
旧 helper／扫描器存于 `output/benchmarks/svg-filter-20261031/artifacts/`，
构建和测试日志位于其父目录。默认 benchmark 路径依赖这些已存档基线和上一轮
公式缓存；也可以通过 pydantic-settings CLI 参数显式指定。

当前 SVG 阶段仍有约 0.82 秒，后续可以细分 SVG 读取、规范化、子资源哈希和
sidecar 检查。应以这次输出一致的基线继续定位，不能直接跳过缓存依赖验证。
完整预览仍需约 4.24 秒，DOCX writer、最终封装和 PDF 生成仍有独立成本。
